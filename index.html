A way to write CSS, not a framework

Write the HTML once.
Let CSS compose the experience.

Atmosphere organizes plain CSS so one page can be read as a document, worked in as a workspace, or shown as slides by changing a single attribute. Nothing is re-rendered, so a half-written note, a selection and keyboard focus survive the switch. There is no build step: registered custom properties, container style queries and cascade layers do the work.

If you know Tailwind: Tailwind writes each decision into each element’s class list. Atmosphere writes what each element is into the markup, then makes the decisions once, in the stylesheet, from a few named choices.

2 · Compared with Tailwind

Same problem. A different home for decisions.

Tailwind and Atmosphere push back on the same thing: hand-written CSS that drifts into arbitrary values, invented class names and rules nobody can find. Tailwind moves styling into the markup, one utility at a time. Atmosphere keeps meaning in the markup and moves decisions into the cascade, where one rule serves every element that shares a meaning.

The task: the guide sits under the document while reading, takes a left column in a wide workspace, and becomes a drawer when presenting.

What each approach optimizes

QuestionTailwindAtmosphere
How are arbitrary values prevented? A theme scale: p-4, not 13px. The escape hatch is p-[13px]. @property rejects choices outside the vocabulary. Quantities are named steps such as data-gap="open". There is no arbitrary-value syntax.
What must you name? Nothing. Utilities replace class names. Only meanings that a rule consumes: what a thing is, what it relates to, its parts. Never wrappers.
What does one element tell you? How it looks, in every context. What it is and how much room it asks for. How it looks is one rule away, shared by everything like it.
Where do responsive, theme and mode rules go? A variant per context on each element: lg:, dark:, group-data-[…]:. Named choices on the host, resolved once with @container style() and container size queries.
How do you restyle everything? Redefine theme variables (v4) to change the scale. Which step each element uses stays in its class list. A Look swaps tokens and density rescales steps. The markup does not change.
How do you add a presentation? Edit every element that should behave differently. Add one recipe. Existing bindings apply.
What tooling is required? A build step (CLI or bundler plugin), plus editor support. None. The browser evaluates plain CSS.
What does the browser need? A modern browser; v4 itself relies on cascade layers and @property. The same, plus container style queries on custom properties. Without them this page stays a readable document.

3 · Compose your CSS

Seven moves, in the order you write them.

Each snippet is adapted from at.simple.css, the single stylesheet behind the demo above. Read that file top to bottom and you will meet these moves in this order.

  1. Declare the order of concerns once.

    Give each concern its own cascade layer. When two rules conflict, the later layer wins regardless of selector specificity, so you never need !important or longer selectors.

    Atmosphere’s Layer concern is named presence here so it is not confused with CSS @layer.

    @layer vocabulary, lens, components,
       layout, presence, lattice, look, life;

  2. Register a small vocabulary.

    Turn each decision into a registered custom property with a fixed list of values. The browser rejects anything else, so a typo falls back to the inherited or initial value instead of leaking into the layout. It is the constraint Tailwind gets from its theme, enforced by the engine.

    @property --navigation {
  syntax: "auto | embedded | on-demand";
  inherits: true;
  initial-value: auto;
}
/* --navigation: sideways;  → invalid, falls back to auto */

  3. Write each experience as plain defaults.

    A recipe, which Atmosphere calls a Lens, is a set of declarations in an early layer. Switching experience changes one attribute. Anything more explicit, such as an inline style set by a control, outranks it without a fight.

    @layer lens {
  [data-lens="workspace"]    { --arrangement: alongside; }
  [data-lens="presentation"] { --arrangement: focus;
                               --path: slides; }
}

<!-- An explicit policy outranks any layered recipe -->
<body data-lens="presentation" style="--navigation: embedded">

  4. Bind meaning to places, never positions.

    The markup declares relationships. One rule per relationship turns it into a responsibility and a named grid area. Each arrangement decides where those areas go. Nothing in the HTML says left, right or drawer.

    [data-relation="navigates"][data-target="document"] {
  --responsibility: navigator;
  --place: var(--place-navigator, supporting);
}
.scene > [data-relation] { grid-area: var(--place); }

  5. Resolve named choices with style queries.

    Give each tool one job. @container style() picks between named options, var() carries facts to the rules that use them, and calc() or clamp() compute quantities.

    @container composition style(--arrangement: alongside) {
  .scene {
    --place-navigator: navigation;
    --scene-areas: "navigation work inspection";
  }
}
.scene { grid-template-areas: var(--scene-areas); }

  6. Publish a token where concerns meet.

    Presence decides whether the guide stays in the layout; Layout owns the grid. Instead of one overriding the other, presence publishes a fact and layout reads it, releasing only the guide’s slot. The notes keep theirs.

    /* presence: decide, then publish */
@container experience style(--navigation: on-demand) {
  .composition { --navigation-presence: on-demand; }
}
/* layout: consume */
@container composition style(--arrangement: alongside)
                   and style(--navigation-presence: on-demand) {
  .scene { --scene-areas: "work inspection"; }
}

  7. Scale with named steps; paint with tokens.

    Quantities are steps on a scale, never raw lengths. Change the rhythm and every consumer moves together. In the full system, call-site quantities use named locals such as data-gap="open". The razor: if changing the look or density cannot move a value, it is a hardcode.

    @container experience style(--rhythm: compact) {
  .composition { --space-scale: 0.7; }
}
@container experience style(--rhythm: spacious) {
  .composition { --space-scale: 1.4; }
}

.scene { gap: calc(var(--space-unit) * var(--space-scale)); }
.scene > aside { background: var(--surface); }

The one gotcha: why there are two containers

A style query reads an ancestor, never the element itself. So the demo keeps choices on the host (body, named experience), derived facts one level down (.composition), and the rules that use both on elements inside them. If a style query seems to do nothing, check that it is asking an ancestor.

4 · File each rule

Ask which question a declaration answers.

File by the decision, not the property name. Padding is usually Layout, but a part’s own intrinsic padding belongs to Components. When two homes need the same fact, one publishes a token and the other reads it.

HomeThe question it answersTypical declarations
Components What shape does a part need to hold its content? box-sizing, resets, intrinsic padding
Layout Where does each responsibility belong? display: grid | flex, grid-template-*, grid-area, gap, width, margin
Layer (presence here) What stays in place, floats or appears on demand? position: sticky | fixed, z-index, [popover], ::backdrop, <dialog>
Lattice How do I move through the content? overflow, scroll-snap-*, scroll timelines, view-transition-name
Look What does it look like? color, background, border, border-radius, font-*, shadows
Life How does it respond and change? transition, animation, hover feedback, prefers-reduced-motion
Lens What experience should these choices serve? Only defaults for the vocabulary, such as --arrangement and --path
Locals How much, right here? Named steps: data-gap, data-pad, data-cols (in at.local.css)

Before you commit a rule

  • No visual words in markup. Not left, blue or big. Name responsibilities and relationships.
  • Every name has a consumer. A rule, a behavior or a test reads it. Do not label wrappers.
  • One decision, one home. If two sheets set a property for the same reason, publish a token instead.
  • Defaults early, policy late. Recipes go in an early layer; explicit choices go on the host. Never !important.
  • Same nodes, always. A presentation change never replaces an interactive element. That is why drafts and focus survive.
  • Fallbacks stay usable. Detect support before revealing controls, and keep the plain document readable.

5 · When it fits

Choose by how often the presentation changes.

Reach for Tailwind when…

  • Each page has one presentation.
  • Your team values fast, consistent styling at the call site and its ecosystem.
  • You are prototyping and the page will not need to recompose.

Reach for Atmosphere when…

  • The same content must be read, worked in and presented.
  • Themes, density and user preferences should restyle everything without touching markup.
  • Work in progress, such as drafts, selection and focus, must survive a change of presentation.
  • You want no build step and no dependency.

What it costs

  • Semantic HTML and a shared vocabulary that the team agrees on.
  • Container style queries on custom properties are newer than the rest of CSS. Test your target browsers and keep the fallback readable.
